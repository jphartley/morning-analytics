# Proposal

## Why

The Black Forest Labs trial did not meet the image-quality bar, so Midjourney/Discord remains the chosen provider. BFL credentials have already been removed from the local environment following the reported Railway incident; the app and setup guidance should now reflect a dormant trial while preserving the work needed to evaluate another provider later.

## What Changes

- Retain the BFL adapter and mocked tests, but disable its application generation routes unless it is explicitly configured as an active trial candidate.
- Separate known provider identities from availability for new generation, preserving all existing BFL images, attribution, and history.
- Add a server-controlled optional trial candidate. An absent candidate means no active trial, no provider picker, and no Dual mode; existing override and Dual authorization flags remain additional gates.
- Replace the hardcoded BFL/Midjourney comparison pair with the configured candidate plus Midjourney, retaining shared orchestration, exact-prompt comparison, diagnostics, partial success, and storage.
- Restore unavailable saved browser selections to the deployment default; reject direct requests for disabled providers before external calls.
- Reduce trial configuration to two server flags with derived browser metadata; remove the legacy public default and migrate queue-generated mock environments.
- Lazy-load the retained BFL adapter only when invoked, remove the standalone paid smoke script and unused preset helper, and centralize provider labels.
- Clean BFL activation instructions and unused BFL settings from normal environment setup, including the existing local `app/.env.local`, without restoring keys or exposing unrelated values. Preserve adapter setup details and the trial outcome in a dedicated experiment reference.
- **BREAKING**: Legacy public-only defaults and independently configured public trial flags are no longer honored. Existing BFL defaults and old trial flags alone will no longer enable BFL or Dual mode. Production must use Midjourney and explicitly deploy any variable changes.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `image-provider-selection`: Separate identity from availability, default trials to dormant, gate trial choices, and configure the comparison candidate explicitly.
- `image-generation`: Compare Midjourney with the configured candidate and preserve display of attributed results from disabled providers.
- `image-regeneration`: Apply the same availability checks and configured comparison pair to regeneration.
- `analysis-storage`: Preserve disabled-provider provenance and use configured comparison order for new batches.
- `openspec-delivery-queue`: Generate and recognize mock candidate environments using the canonical provider setting.

## Impact

- Provider registry, shared selection types, browser preset restoration, picker visibility, build-time public configuration, generation/regeneration actions, and their existing tests.
- No BFL adapter deletion, new provider implementation, new dependency, database migration, history deletion, or change to Midjourney capture behavior. Durable jobs and server-session/role hardening remain outside scope.
- Documentation: normal setup and Railway guidance, image architecture, experiment reference, and relevant technical-debt wording. Archived OpenSpec changes remain historical records.
- Environment / Railway variables: new optional server-only `IMAGE_PROVIDER_TRIAL_CANDIDATE` (unset for dormancy); changed deployment settings `IMAGE_GENERATION_PROVIDER` (production `midjourney`) and the two existing server override/Dual flags (false for dormant operation); remove obsolete `BLACK_FOREST_LABS_*` settings from active local/production setup if present. Do not introduce a second manually maintained public candidate variable. Remove `NEXT_PUBLIC_IMAGE_PROVIDER`, `NEXT_PUBLIC_IMAGE_PROVIDER_TEST_OVERRIDE_ENABLED`, and `NEXT_PUBLIC_IMAGE_PROVIDER_DUAL_MODE_ENABLED`; operators configure only the canonical default, candidate, and two server flags. Derived browser metadata is generated by the app, not set separately in Railway.
- Railway changes are a manual production-environment handoff, not an automated action in this change. Review staged changes and deploy after every variable change; `NEXT_PUBLIC_*` values require a rebuild. Local `.env.local` is untracked and must never enter a commit or PR.
